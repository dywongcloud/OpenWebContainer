owc-blob-file-ctor-no-validation resolved witness-49b83355102cde66 2026-11-02T06:18:59Z

Symptom
  new Blob(1) and new File() are accepted where host node v24.15.0 refuses both:
  the container answered a Blob of size 0 for every source that is not a
  sequence -- a number, a string, a boolean, a bigint, a symbol, a function, a
  plain object -- and a File of name 'undefined' for a File made with fewer than
  two arguments, where the host throws
  'The "sources" argument must be a sequence. Received type number (1)'
  (ERR_INVALID_ARG_TYPE) and
  'The "fileBits" and "fileName" arguments must be specified' (ERR_MISSING_ARGS).
  A File made with no name threw its own message here -- 'The "fileName"
  argument must be specified' -- and no code at all. The options object was
  never checked either: new Blob(['ab'], 5) and { endings: 'bogus' } were both
  accepted where the host raises 'The "options" argument must be a dictionary'
  and "The property 'options.endings' is invalid".

Fix
  packages/core/src/process/executors/node/runtime/guest/buffer-fs.ts: the Blob
  constructor takes its sources through blobSourcesOf, which accepts undefined
  and anything iterable behind an object and refuses the rest -- a string
  iterates and is still refused -- naming what it was handed the way node names
  it, and reads its options through blobOptionsOf, which accepts undefined,
  null, an object and a function, refuses a primitive as not a dictionary, and
  refuses an endings that is neither 'transparent' nor 'native' with
  ERR_INVALID_ARG_VALUE. A symbol inside the sequence is refused with the
  TypeError node raises rather than written as the name it prints as. File
  counts its arguments before its bits are read, so a File made with one is
  ERR_MISSING_ARGS even when the one is a shape a Blob would have taken, reads
  a given lastModified as a number -- a value no number can be made of leaves
  none -- and keeps the moment it was made for one that was handed nothing.
  Blob.length is 0 and File.length 2, the arities the host answers. The two
  errors are made by blobErr, which puts the code on the error and into the line
  its stack opens with, as node does, and answers a toString carrying it, while
  the name stays the plain one.
  packages/core/src/process/executors/node/runtime/guest/globals.ts: the global
  File is the one require('buffer') hands out, so the two are one class, and the
  name and the date a File carries are its prototype's rather than fields
  written onto each instance, which is what leaves Object.keys empty.
  packages/core/src/process/executors/node/runtime/guest/util-assert.ts:
  formatErrorStack reports a stack that already opens with the line node writes
  -- one carrying the code -- as it stands, instead of putting a second header
  of the name and the message in front of it. An error a program gave a code of
  its own is untouched: its stack carries no such line.

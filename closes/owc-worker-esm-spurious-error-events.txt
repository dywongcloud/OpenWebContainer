Symptom
  A Worker whose entry is an ES module emitted 'error' events the host does not. `new Worker(entry)`
  over an .mjs entry that imports another ES module and posts a message worked -- the parent received
  {"esm":true,"tag":"ESMDEP","isMain":false} and exit 0 -- but only here did it also receive two
  'error' events first, each a TypeError with no code and the engine's bare message 'not a function'.
  It happened with no options, with {} and with {stdout:false}. A Worker whose entry was a .js file
  got no error event on either side.

Cause
  One spurious error per ES module file in the worker's graph: the host names every file it compiles
  as an ES module to the guest, in process.ts, through `this.callApi('markEsmFile', [file, entry])` --
  and no guest source has ever defined api.markEsmFile. The call therefore failed every time with the
  engine's TypeError 'not a function', and markEsmFile's own catch swallowed the failure, so nothing
  was ever visible. What was not swallowed is what the host does with an error before it swallows it:
  callApi hands it to guestFailure(), which formats it with the guest's own api.formatUncaught, and
  in a worker thread that formatter is wrapped (cpWireWorkerErrors in
  packages/core/src/process/executors/node/runtime/guest/modules/child.ts) to also report the error to
  the parent. So a host call that had always failed silently became, inside a worker, one 'error'
  event per module compiled: 1 for an entry with no imports, 1 for an entry importing a builtin, 2 for
  an entry importing one file, and 1 before the real ERR_MODULE_NOT_FOUND for an entry whose import
  does not resolve. The events arrived after 'online' and before the worker's own 'message'.

Fix
  packages/core/src/process/executors/node/runtime/guest/modules/child.ts
    The guest answers the call: `api.markEsmFile` is installed when it is missing, so the host's
    per-module question succeeds and there is no engine error left for guestFailure to format and for
    a worker to report. Nothing else moves: an error the worker really raises still reaches the parent
    through the same wire, in the same order.
  Pushed as abd60258b5f94ab7b7a612c2338ae4dda8943c1b, built on origin/main with a temporary index.

Residual, not this row
  markEsmFile exists so a frame the engine names in an ES module can be rendered the way node renders
  one, as a file URL, and the guest has no frame marker to hand the name to: it answers the call and
  keeps nothing. The rendering is still the path -- an .mjs entry that throws prints
  '/app/w-esm-throw.mjs:2:7' where host node 24.15 prints
  'file:///private/var/folders/.../w-esm-throw.mjs:2:7', and the host's caret and its loader frames
  behind the throw are absent here. Filed as row owc-esm-frame-not-a-file-url.
  A second difference met on the way and not touched: an ESM *entry* whose import does not resolve is
  reported by host node 24.15 as the engine's own report (a 'node:internal/modules/esm/resolve' frame
  and the ERR_MODULE_NOT_FOUND with its url), while this container prints the short
  'Error: Cannot find module ... imported from ...'; the same failure inside a Worker agrees with the
  host on both sides.

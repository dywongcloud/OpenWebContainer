Status: resolved

Symptom
  An ES module entry that installs process.on('uncaughtException', ...) and then throws never ran
  that handler here: the process wrote the fatal report -- 'file:///app/w.mjs:2', the line, the caret,
  'Error: top boom', the frame, the ESM loader frames, 'Node.js v24.15.0' -- and exited 1, where host
  node 24.15 gives the error to the handler, prints what the handler prints and exits 0. It is the
  entry's own body alone: the same handler over a throw out of a timer agreed with the host, and the
  same handler in a CommonJS entry agreed, which is what said the module kind was what decided it.

Cause
  runEsmEntry (process.ts) raised the failure of the entry's evaluation at the host level --
  `throw this.guestFailure(...)` over the rejected evaluation promise, and over a result.error the
  engine answered with -- so it never reached the guest at all and no listener was ever asked. A
  CommonJS entry goes through guestCall('runMain', [file]), whose error the guest hands to its own
  uncaught route before it throws it back: emitUncaught in guest/loader.ts counts the listeners when
  the error is in hand, gives them the error and lets the run go on, and only with none does it throw,
  which is what leaves the host's report. That is the whole of the difference between the two kinds.

Fix
  packages/core/src/process/executors/node/runtime/guest/loader.ts
    api.esmEntryFailure -- the route a CommonJS entry's failure takes, for the failure of an ES module
    entry's own body: the error is handed to emitUncaught, which gives it to an 'uncaughtException'
    listener and leaves the run to it, and throws it back when there is none. A listener registered at
    the top of the module is therefore a listener the error finds, as it does on the host.
  packages/core/src/process/executors/node/process.ts
    runEsmEntry answers with the guest's route instead of raising the failure itself, in both shapes
    the failure comes in -- an error the engine answered the evaluation with, and a rejected evaluation
    promise -- and hands the handle over on the way, on every way out of the call: one the host still
    held when the runtime was freed is what QuickJS asserts on at teardown. startEntry takes the
    promise of a run that suspended inside a listener as the run's own. A failure of the graph and not
    of the body -- a specifier that resolves to nothing, a module no loader can read, one that will not
    parse -- is left to the report it has always had: host node 24.15 writes such a one itself and
    hands it to no listener, which is what a listener a module the entry imports first had already
    registered measured on host node 24.15.

Symptom
  The whole errno table was dumped as JSON on both sides: 79 keys, the same key
  set, but the values were Linux's and not the host's. Host node v24.15.0 on
  this macOS box reads EAGAIN 35, EWOULDBLOCK 35, ECONNRESET 54, EADDRINUSE 48,
  ECONNREFUSED 61, ETIMEDOUT 60, ELOOP 62, ENOTEMPTY 66, EOPNOTSUPP 102,
  ENOTSUP 45, EPROTO 100; the container read EAGAIN 11, EWOULDBLOCK 11,
  ECONNRESET 104, EADDRINUSE 98, ECONNREFUSED 111, ETIMEDOUT 110, ELOOP 40,
  ENOTEMPTY 39, EOPNOTSUPP 95, ENOTSUP 95, EPROTO 71 -- Linux's numbers, so
  ENOTSUP and EOPNOTSUPP collapsed onto one value where the host keeps them
  apart. 47 of the 79 names were wrong. os.constants.priority (6 entries),
  os.constants.signals (31 entries) and the constant group key set were
  byte-identical throughout.
  Fixed as 0dc08daacfab3d9d263e317f184518d52ead0b43, parent
  48cfe0b2cdf592223aac7abb132648f17d0b312c, parent origin/main
  89804194c0fb072f8a4e1471e41e0a6f8c3cc223.

Fix
  packages/core/src/process/executors/node/runtime/guest/misc.ts: BF.os's errno
  table now carries this platform's numbers instead of Linux's. Same key set,
  79 names, same alphabetical order, so JSON.stringify(os.constants.errno) is
  byte-identical to the host's. The numbers the errors this runtime raises carry
  are this platform's too -- the ERRNOS table buffer-fs keeps already reads
  ENOTSUP -45, ENOTEMPTY -66, ELOOP -62, ENOSYS -78 -- so os.constants.errno and
  an error's own errno now name the same thing. priority and signals are
  untouched.

Row: owc-error-code-line-missing
Witness: 1793604131165-6913-fe570513f8655ca9
Status: resolved

Symptom
  An uncaught error carrying a `code` printed without the `[CODE]` decoration on the line the report
  opens with and without the `code:` trailer behind the frames, where host node 24.15 prints both.
  Measured: `Buffer.from(1)` -- host writes "TypeError [ERR_INVALID_ARG_TYPE]: The first argument
  must be of type string or an instance of Buffer, ArrayBuffer, or Array or an Array-like Object.
  Received type number (1)" and then "  code: 'ERR_INVALID_ARG_TYPE'" in braces behind the last
  frame; the container wrote "TypeError: The first argument must be of type string or an instance of
  Buffer, ArrayBuffer, or Array" and nothing behind the frames at all. Proved with a plain TypeError
  a program builds itself, so the reporter and not the error was at fault: `e.code = 'ERR_MY_OWN'`
  on a `new Error('boom')` is `Error: boom` followed by "{\n  code: 'ERR_MY_OWN'\n}" on the host and
  was `Error: boom` alone here.

Cause
  Two things the uncaught reporter never did, and one thing it could not know.
  (1) `api.formatUncaught` (globals.ts) answered `formatErrorStack(err)` -- the report alone. The
      properties behind it are what node's own handler adds, and it adds them by inspecting the
      error: the report is the prefix and the own properties the report is not made of go behind it
      in braces. Nothing here ever wrote that second half, so no error of any kind carried its
      `code`, its `errno`, its `syscall` or its `path` into the report.
  (2) `formatErrorStack` (util-assert.ts) built the opening line out of the name and the message
      alone. Host node writes the code into that line as it builds the error -- an error of its own
      carries 'TypeError [ERR_INVALID_ARG_TYPE]' in its stack while the name it answers is still the
      plain 'TypeError' -- and this container's own errors are built the way a program builds them,
      with the code assigned afterwards, so the line came out with the name alone.
  (3) Which is also what makes (2) a thing the reporter has to be told: a program's own error with
      a code of its own is reported by host node 24.15 as 'TypeError: boom', with no brackets, so
      the decoration cannot be written for every error that carries a code. Whether the container
      or the program built the error is not something the report can ask of the error afterwards --
      the frames of the bootstrap's are gone from the stack by then -- so it is asked where the
      frames still name their author, at the moment the error is built, and kept on it.

Fix
  packages/core/src/process/executors/node/runtime/guest/util-assert.ts
    uncaughtReportOf -- what node writes for an uncaught error: the whole of what 'util.inspect'
    writes for the value, the report and the properties behind it, and not the report alone.
    formatErrorStack -- the opening line carries '[<code>]' behind the name when the error is one
    this container raised with one of node's own codes, the 'ERR_...' ones; the 'ENOENT' and 'EBADF'
    of a file that would not open belong to another class of error of node's and still print with no
    brackets, as they do there. The header the stack itself opens with is dropped in front of it the
    way it already was for a subclass, so the line is written once and not twice.
  packages/core/src/process/executors/node/runtime/guest/globals.ts
    raisedByContainer -- whether the first frame behind the wrapper's own is a frame of the
    bootstrap's (or a native call with the bootstrap behind it), which is what says the container
    built the error and not the program. Asked in installStackHeader's Shim, where the frames still
    name their author, and kept on the error as '__owcRaised' -- non-enumerable, so nothing that
    inspects the error sees it -- because the rewritten stack holds nothing of the bootstrap's.
    api.formatUncaught -- uncaughtReportOf for an Error, inspectValue for anything else, as before.
  packages/core/src/process/executors/node/runtime/guest/buffer-fs.ts
    Buffer.from's refusal of an argument of no type it takes is given the code the host's own
    carries, 'ERR_INVALID_ARG_TYPE', through the bufErr the rest of the file already uses -- the one
    site of the row's measured example that answered with a bare TypeError and no code at all.

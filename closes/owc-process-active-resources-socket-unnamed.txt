Symptom
  `process.getActiveResourcesInfo()` named no socket here: host node v24.15.0 answers
  ["TCPServerWrap"] for a listening server, ["TCPServerWrap","TCPSocketWrap"] once a socket dials,
  ["ConnectWrap","TCPServerWrap","TCPSocketWrap"] while the connect is in flight, ["UDPWrap"] for a
  datagram socket and PipeWrap for a unix-path handle, and none of the three once the server is closed
  and the socket destroyed. The virtual hub kept no list of the handles it made, so globals.ts had
  nothing to read their kinds off: it answered [] throughout, and still did after the earlier fix that
  named the file request, the pipe and the timers. Host also names GetAddrInfoReqWrap for a DNS lookup
  of a name (in flight and in its callback), none for an IP literal, and SimpleShutdownWrap at a socket
  shutdown; those three requests live in dns.ts and the shutdown path, not in this row's grant.

Fix
  packages/core/src/process/executors/node/runtime/guest/modules/net.ts
    A list of the open, referenced handles next to netRefresh, which already knows whether an owner
    holds a ref. A listening TCP server registers TCPServerWrap (a path listener a PipeWrap); a dialling
    socket registers TCPSocketWrap (a path one a PipeWrap) and a ConnectWrap request; an accepted socket
    its own TCPSocketWrap; a datagram socket a UDPWrap from the moment it is made. A listener is named
    from the turn after listen(), a handle leaves the walk on the turn after its close callback, and
    ref()/unref() add and drop it. The requests are reported ahead of the handles, oldest first, as
    node's own walk reports them.
  packages/core/src/process/executors/node/runtime/guest/globals.ts
    activeResourceNames() reads the net list through a global hook installed when the net family loads,
    so a run that required no net names no socket; timers, immediates and file requests keep their own
    names and the FSReqCallback/PipeWrap/timer ordering.

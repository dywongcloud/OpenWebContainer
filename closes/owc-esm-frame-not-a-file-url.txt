Symptom
  A frame in an ES module is a path here, where host node 24.15 writes a file URL. An entry that
  imports ./dep.mjs and then throws printed '/app/w.mjs:2' in the caret banner and
  '    at /app/w.mjs:2:7' as its one frame, where the host prints 'file:///app/w.mjs:2' and
  '    at file:///app/w.mjs:2:7' and follows them with three frames of its own loader --
  '    at ModuleJob.run (node:internal/modules/esm/module_job:437:25)',
  '    at async node:internal/modules/esm/loader:639:26' and
  '    at async asyncRunEntryPointWithESMLoader (node:internal/modules/run_main:101:5)' -- none of
  which this container wrote. The same in a frame of a function the entry imported, in the frame of a
  module whose own body threw while the entry imported it, and in a stack the program captured with
  Error.captureStackTrace. The caret also stood under the 'throw', as it does for a CommonJS body,
  where the host marks an ES module at the column the frame names. A CommonJS body was right.

Cause
  Host node names a file it compiled as an ES module by its URL, and which files those are is
  something only its resolver knows -- a .js file is a module or not by the package it sits in -- so
  the host names each one to the guest as it compiles it, in process.ts, through
  this.callApi('markEsmFile', [file, entry]). No guest source answered that call at all before
  abd6025, and since it the guest has answered it keeping nothing: that answer is what stopped a
  worker from reporting the failed call as an 'error' event, and it is all that answer does. So the
  guest's frame renderer, guestFramesOf in globals.ts, had no way to tell a frame in an ES module
  from one in a CommonJS body, and named every file by its path; and the host's report -- which puts
  the caret block in front of the guest's own stack and reads the file's source out of the frame --
  knew nothing of a URL either, so it could not print one and could not point its caret at the
  column an ES module is marked at.

Fix
  packages/core/src/process/executors/node/runtime/guest/globals.ts
    The guest keeps the mark: api.markEsmFile records the file, and whether it is one the run's entry
    loaded, so the answer to the host's question is a fact the frame renderer can read. A frame in a
    marked file is rendered with the file's URL and not its path, in both shapes a frame has -- named,
    '    at boom (file:///app/dep.mjs:2:9)', and bare, '    at file:///app/w.mjs:2:1' -- and behind
    the frames of a run whose outermost frame is the module the entry loaded, the three frames of
    node's ESM loader are put, the way the CommonJS loader's are put behind a body it compiled. A
    frame in any other file -- a CommonJS body, one of node's internals, a module a later dynamic
    import loaded -- is the frame it was. The note this container keeps of the place an 'exit'
    handler failed at reads the file behind the URL, so it names what it named before.
  packages/core/src/process/executors/node/process.ts
    The host's report reads a frame that names a file by its URL: scriptSiteOf takes a file: URL as a
    frame's file as readily as a path, the banner and the frame print the name the frame shows -- the
    URL for an ES module, the path for everything else -- and the source of the line is read through
    the path the URL carries. The caret of a report over a file URL is put at the column the frame
    names, which is where host node marks an ES module, and not at the 'throw' in front of it, which
    is where a CommonJS body is marked.

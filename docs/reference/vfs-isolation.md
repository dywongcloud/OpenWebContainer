# VFS isolation is realm-scoped, not per-container (measured)

The container root filesystem is one module-level mount, not per-instance state: `zenfs-core.ts:17-26` declares `let rootMounted = false`, `mountContainerRoot()` early-returns when that flag is set, and mounts a single `new InMemoryStore('owc-root')` at `/`, so VFS sharing is REALM-SCOPED and the isolation boundary is the process/realm that loads the module, not the `OpenWebContainer` instance. `ContainerOptions` (`container.ts:28-38`) exposes only `debug`, `onServerListen`, `onServerClose` and `guestBudgetMs` — no fs/storage/shared/persist option — and `dispose()` (`container.ts:603-621`) stops servers, kills processes, clears output callbacks and disposes the network manager but does not unmount the root, so there is no in-realm reset/clear API. The explicit reset/clear path for a measurement harness is therefore a FRESH NODE PROCESS per boot (a fresh module realm), the "one fresh isolated container process per case" convention that cmdv1 and drain-npm-g-residual1's own Phase A used to obtain a clean root. This refutes the claim that fresh-boot isolation is defeated: at two memory points (loaded: load 33.06, free 62 MB; free: load 33.06, free 325 MB), two reps per point, four runs total on host node v24.15.0 against built dist sha256 `e7f547750075e2b47c509c67af0bb7aba75e05c3a5995a40b0e30edf9642f1de`, a unique `/app/MARKER.txt` written through a first container and read after `dispose()` by a second container in the SAME realm survived in 4/4 runs (`cat` exit 0, stdout equal to the marker), while a separate fresh node process per boot saw no marker in 4/4 runs. The measured sharing is intentional realm-scoped persistence, not a fresh-boot isolation defect; harnesses that need isolation must boot each case in its own process instead of reusing a realm.

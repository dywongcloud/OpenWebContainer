# Isolation boundaries

  - **SUPERSEDED**: At the time of the headful Chrome 157 measurement the :5173 playground document response carried no Cross-Origin-Opener-Policy and no Cross-Origin-Embedder-Policy (self.crossOriginIsolated=false, typeof SharedArrayBuffer=undefined, isSecureContext=true) while the Web IDE still booted; it records the tree as measured, not the current code. On the current tree apps/playground/vite.config.ts sets Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp for both server and preview, so verify the response headers your own deployment actually serves before relying on SharedArrayBuffer.
  - **SUPERSEDED**: At the time of that measurement there was no WebContainer.boot-style coep option: ContainerOptions carried only debug/maxProcesses/memoryLimit/onServerListen/onServerClose and WorkerInitOptions only debug/memoryLimit, so the require-corp | credentialless | none union and a coep value fixed at first boot could not be honoured on a later reboot. On the current tree ContainerOptions.coep and WorkerInitOptions.coep accept 'require-corp' | 'credentialless' | 'none', and packages/api/src/worker/bridge.ts validates the value and locks it at first boot.
  - Direct-TCP database drivers (MongoDB, Mongoose, PostgreSQL, MySQL) cannot connect from a browser-hosted container; use an HTTP/API-accessible provider such as Neon serverless Postgres instead, because only the container virtual TCP and page-level fetch exist.
  - Guest fetch is not browser or host undici parity: Node fetch is built on undici, an HTTP/1.1 client written from scratch for Node, while this container serves its own undici module over its own http/https client, so a program cannot assume host or browser fetch, connection and stream behaviour.
